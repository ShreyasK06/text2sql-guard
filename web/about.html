Ask the database anything your role may see.

text2sql-guard turns a question into SQL, then runs it through eight stages before a read-only database user returns masked, role-scoped rows. Six of those stages can refuse it, and each refusal says why.

Open the console Watch the recorded demo

A real response from the recorded demo: an analyst asks the system to delete all orders.

Eight stages. Six can say no.

Defense in depth means no single check carries the whole load. The input guard is pattern based and can be paraphrased around, so the allowlist, the AST rules, the cost gate and the database itself each have to hold on their own.

  1. Input guardScreens the question for destructive intent, override phrasing and requests for data your role cannot read.Can refuse
  2. Schema retrievalThe model is shown only the tables and columns your role may see.Narrows the prompt
  3. SQL generationThe model writes SQL. Here that is a deterministic mock, not a live LLM.Never trusted
  4. AllowlistEvery table, column and function must be listed for the role. Default deny.Can refuse
  5. AST rulesSELECT only, one statement, forced LIMIT, caps on joins and nesting.Can refuse
  6. EXPLAIN cost gatePostgres plans the query without running it. Expensive plans are refused.Can refuse
  7. Sandboxed executionA read-only database user with column grants, row-level security and a timeout.Can refuse
  8. Output guardMasks sensitive columns, scrubs PII patterns, caps cell size.Rewrites results

When a stage cannot decide, the answer is no.

Fail closed

SQL that cannot be parsed is refused, not guessed at. If the EXPLAIN step fails, that is a block. A role limited to one region that arrives without a region is refused.

Every block carries a rule id and a plain-language reason, so a refusal can be read, audited and argued with.

Allowlist over blocklist

Nothing is permitted because it was not forbidden. A table, column or function that is not listed for a role does not exist for it.

One file, policies/policy.yaml, drives the validator, the output guard and the database grants, so the rules the code enforces and the rules the database enforces cannot drift apart. Enforcement lives in code and in database permissions, never in the prompt.

What it does, and what it does not.

What it does

  • Applies the role's allowlist and masks sensitive columns before anything is displayed.
  • Restricts a regional manager to one region with row-level security in the database.
  • Refuses anything that is not a single, bounded SELECT, and runs the rest as a read-only user.
  • Logs every request with the stage that decided it.
  • Is covered by an offline test suite that includes tests against a real PostgreSQL 16.

What it does not

  • It has no measured attack block rate. The evaluation holds no attack items.
  • It has never been run against a live language model. Only the mock provider was used.
  • It has no authentication. Role and region are asserted by the caller in this demo.
  • Its input guard is pattern based, so paraphrased intent can get past that stage.
  • Masking is column and pattern based, so sensitive values inside free text are only partly covered.
  • It sometimes refuses a legitimate query. See the numbers below.

Run it on your own machine.

Python 3.11 or newer, and Docker for the demo PostgreSQL. The default provider is a deterministic mock, so no API key is needed.

python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python scripts\db.py up
.venv\Scripts\python -m uvicorn app.api.main:app
# then open http://127.0.0.1:8000

Without Docker, the recorded demo works from any static host.
